# Coding Standards

Established at T001. These rules apply to all future implementation
tasks (T010 onward). Tool config files are added by the task that first
creates the relevant app (`apps/api` in T010, `apps/web` in T011) using
the exact rules below, so the config doesn't fight that task's
scaffolding tool. `.editorconfig` and `.gitattributes` (repo-wide,
tool-agnostic) are already in place as of this task.

## 1. Python formatting

- Formatter: **Black**, default line length 88.
- Import sorting: **Ruff's isort rules** (`I`), stdlib → third-party →
  local, one blank line between groups, no wildcard imports.
- Applied via `ruff format` + `ruff check --fix` (Ruff runs both to
  avoid two tools). Config lands in `apps/api/pyproject.toml` at T010.

## 2. Python linting

- **Ruff**, rule sets: `E`, `F`, `I`, `B`, `UP`, `SIM`, `C4`. Treat
  warnings as errors in CI (T002).
- No bare `except:`; catch specific exception types.
- No unused imports/variables (enforced by `F`).

## 3. Python type checking

- **mypy** in strict-ish mode: `disallow_untyped_defs`,
  `warn_return_any`, `no_implicit_optional`. Full `--strict` is a
  stretch goal once the domain layer stabilizes — don't block early
  tasks on it.
- All service/repository/provider public functions must be typed.

## 4. TypeScript strictness and linting

- `tsconfig.json`: `"strict": true`, `"noUncheckedIndexedAccess": true`,
  no `any` except at explicit, commented I/O boundaries (e.g. raw
  third-party SDK responses pending validation).
- ESLint: `next/core-web-vitals` + `typescript-eslint` recommended,
  plus `no-unused-vars`, `no-console` (allow `console.error`/`warn`).
- Config lands in `apps/web` at T011 (Next.js's own scaffolding tool
  generates a base file; extend it, don't replace it wholesale).

## 5. React / Next.js component conventions

- Functional components only, one component per file.
- File name matches component name in PascalCase
  (`JobStatusBadge.tsx`); route files follow Next.js App Router
  conventions (`page.tsx`, `layout.tsx`).
- Server components by default; add `"use client"` only where
  interactivity requires it.
- No business logic in components beyond presentation/local UI state —
  data fetching and mutations go through a typed API client layer, not
  inline `fetch` calls scattered through components.
- No secrets or server-only config in client-side code
  (`NEXT_PUBLIC_*` only for values safe to expose).

## 6. API naming conventions

- REST, resource-based, plural nouns: `/api/v1/projects`,
  `/api/v1/jobs/{job_id}`.
- Path segments kebab-case if multi-word (`/api/v1/job-runs`).
- JSON field names: **snake_case**, matching the Python/Pydantic
  models directly — no camelCase aliasing layer.
- Response envelope: `{"data": ..., "request_id": ...}` on success,
  `{"error": {...}, "request_id": ...}` on failure (per
  `docs/05_API_DESIGN.md`).
- Job creation and other mutating POSTs accept an idempotency key.

## 7. Database naming conventions

- Tables: snake_case, plural (`projects`, `job_runs`, `records`).
- Columns: snake_case; primary key `id`; foreign keys
  `<singular_table>_id` (e.g. `project_id`).
- Timestamps: `created_at`, `updated_at` (UTC), `deleted_at` only where
  soft-delete is an explicit requirement.
- Enum-like state columns: lowercase snake_case values matching the
  domain state machine exactly (e.g. job `status`).

## 8. Migration rules

- One logical schema change per Alembic migration.
- Every migration implements both `upgrade()` and `downgrade()`.
- No destructive migration (drop column/table, data-lossy type change)
  without an explicit note in the PR/commit describing the recovery
  plan.
- Migration filenames: Alembic's autogenerated
  `<revision>_<slug>.py`; the slug must describe the change, not the
  task ID.

## 9. Test naming and placement

- Layout matches `docs/02_SYSTEM_ARCHITECTURE_DEEP.md`:
  `tests/unit`, `tests/integration`, `tests/provider`, `tests/e2e`.
- Python: `test_<module>.py`, one test file per source module where
  practical; test function names describe behavior
  (`test_job_rejects_transition_from_completed_to_running`).
- Frontend: colocated `*.test.tsx` next to the component, or
  `apps/web/tests/` for broader flows.
- Every task that adds behavior adds or updates tests in the same
  change — no "add tests later" follow-ups.

## 10. Structured logging

- JSON structured logs (Python `logging` + a JSON formatter, or
  `structlog`). Required fields: `timestamp`, `level`, `message`,
  `request_id` (API) or `job_id`/`run_id` (worker), `logger`.
- Never log secrets, API keys, full provider payloads, or raw PII.
  Redact/truncate before logging.
- Log levels: `INFO` for normal lifecycle events (job created, job
  completed), `WARNING` for recoverable anomalies, `ERROR` for
  failures needing attention, `DEBUG` for local development only.

## 11. Git branch and commit conventions

- Branch names: `task/T0NN-short-slug` (e.g. `task/T010-python-env`)
  for task work; `fix/short-slug` for out-of-band fixes.
- Commits: [Conventional Commits](https://www.conventionalcommits.org/)
  style — `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:` —
  with a scope where useful (`feat(worker): add heartbeat`).
- One task = one or more focused commits; don't mix unrelated changes.
- Never commit `.env`, credentials, or generated exports (enforced by
  `.gitignore` from T000).

## 12. Import ordering and unused code

- Python: stdlib, then third-party, then local — one blank line
  between groups (Ruff `I` enforces this).
- TypeScript: external packages, then internal aliases/absolute
  imports, then relative imports.
- No unused imports, variables, or dead code committed — delete rather
  than comment out.

## 13. Error handling

- Each layer raises its own exception types (domain errors in
  `domain/`, provider errors classified via the provider adapter's
  `classify_error`); don't let a raw driver/SDK exception cross a
  layer boundary uncaught.
- API layer converts domain/service exceptions to the structured error
  envelope with an appropriate HTTP status — never leak stack traces
  or internal messages to clients.
- Worker layer classifies failures per the taxonomy in
  `docs/01_SYSTEM_EXPLANATION.md` (configuration, authentication,
  provider rejection, rate/usage limit, transient network, malformed
  response, validation, persistence, export, internal) and only
  retries the classes marked retryable.

## 14. Provider adapters and secrets

- All Google-specific code stays behind the `ProviderAdapter` interface
  (see `docs/16_MEMORY.md` for the exact contract decided at T000);
  nothing outside `providers/` imports a Google SDK/client directly.
- No CAPTCHA-solving, anti-bot/stealth evasion, or access-control
  bypass code, ever — this is a hard project boundary, not a style
  preference.
- All configuration/secrets come from environment variables, validated
  at startup with a clear failure if a required variable is missing.
  Never print/log a config object wholesale; never hardcode a
  credential, even a placeholder-looking one, outside `.env.example`.

## Comments and documentation in code

- Default to no comments. Add one only when the *why* isn't obvious
  from the code itself (a non-obvious constraint, a workaround for a
  specific provider quirk, an invariant a reader could easily violate).
- No docstring templates copied for their own sake — a docstring is
  for information a good name and type signature don't already convey.
